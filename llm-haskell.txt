Both bugs are fixed, all 43 tests pass, and the app boots and serves on port 8008. Here's what was wrong and what I changed.

Root cause 1 — Bomb never detonates: broken clock
Controller.hs built its timestamp from Date#getMilliseconds(), which returns the milliseconds-within-the-current-second field (always 0–999), not a timestamp. Your fuse check t - plantedAt >= 3000 can therefore never be true — both operands are always under 1000, so no bomb ever detonates. (The countdown timer worked only because it accumulates small per-frame deltas, which masked the wraparound.)

Fix: replaced it with M.now, which Miso publicly re-exports from Miso.FFI and which wraps performance.now() — a monotonic millisecond clock. One-line change in [Controller.hs](C:\Users\Izech\Desktop\Code Stuffs\cs 150 removals\src\Controller.hs).

Root cause 2 — Stuck in the bomb: solidity judged at the destination
bombSolid says a bomb is solid exactly when the player does not overlap it. The old moveAxis checked solidity at the candidate new position: the single step that would take you from "overlapping" to "fully clear" always lands on a non-overlapping position, so it was always rejected. You could slide around inside the bomb's cell forever but never complete the exit — exactly the trap you saw.

Fix: solidity is now judged from the player's current position each tick ([Model.hs](C:\Users\Izech\Desktop\Code Stuffs\cs 150 removals\src\Model.hs) moveAxis). While you overlap the bomb it's passable (walk off freely); the moment your hitbox fully clears the cell, the bomb's cell is stamped in as a wall for that collision check, blocking re-entry — matching your spec exactly.

Two other spec violations I fixed while in there
Blast range was unbounded. The old ray recursed down entire corridors. Spec says 1 tile in each cardinal direction, so there's now a bombRange = 1 constant the ray respects.
Explosions lingered (and killed) on destroyed soft blocks. Spec says the soft block is destroyed immediately and the flame does not occupy that cell. ray now returns flame cells and destroyed cells separately (softBlocksDestroyed), and detonateAll destroys only via the latter, so no linger, no kill, no render on that tile.
Also a small one: holding two arrow keys used to produce diagonal movement; inputVector now prioritizes horizontal so movement is strictly orthogonal per spec. Two existing tests actually asserted the buggy behaviors (walking back onto a cleared bomb; flame on the soft-block tile) — I rewrote them to the spec and added regression tests for both of your reported bugs (walk-off: player fully exits the bomb's cell, cleared bomb is solid: cannot walk back onto it). cabal test → all 43 pass.

Your MsgGetTime/MsgSetTime loop re-queues itself immediately after each M.io call, so it spins as fast as the CPU allows rather than once per frame. Root cause: two stacked problems, neither in the server
1. Your replaced files have "backwards" timestamps. When you copied the new PNGs in, Windows preserved their source modification times — Jan 6 2026. But the old placeholder assets your browser had cached were from Oct 5 2026. The dev server (miso's run uses wai-middleware-static) sends only a Last-Modified header, no ETag. So when the browser revalidates its cache asking "has floor.png changed since Oct 5?", the server compares against the file's mtime — Jan 6 — which is before Oct 5, and answers 304 Not Modified. Your browser then keeps drawing the old sprite. That's why restarting the server and reloading didn't help: every conditional request comes back "unchanged."

2. The player sprite can't load at all. Your new player art is named player.jpg, but the code loads resources/player.png — that URL returns 403 (file missing), so even a fully-cleared cache has no player to show.

I also verified the server itself was never the problem: it reads files from disk per request, and the bytes it served hash-identical to what's on disk.

What I changed
Renamed resources/player.jpg → resources/player.png so the filename matches what the code (and your "original filenames" intent) expects. Browsers and canvas sniff the actual bytes, so JPEG content under a .png name renders fine — but if you want it proper, re-export the art as a real PNG named player.png.
